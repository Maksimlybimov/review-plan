# План ревьюирования программного проекта

**Самостоятельная работа № 3.** Планирование ревьюирования программного проекта

---

## 1. Объект ревьюирования

**Объект проверки:** новая версия программного модуля `order_pricing` (расчёт стоимости заказа) в веб-сервисе интернет-магазина. Изменения находятся в ветви `feature/order-pricing-v2` и предназначены для слияния в основную ветвь `main`.

**Состав изменений:**

- функция `calculate_total(order, promo_code)` с новой логикой применения скидок;
- изменение API: эндпоинт `POST /api/orders/price` принимает дополнительное поле `promo_code`;
- модульные тесты в каталоге `tests/test_order_pricing.py`;
- обновление документации API (`docs/api.md`).

**Почему объект требует проверки перед слиянием:**

- модуль напрямую влияет на деньги пользователей: ошибка в округлении или в применении скидки приводит к финансовым потерям или жалобам клиентов;
- изменяется публичный API, поэтому возможна несовместимость с существующими клиентами (мобильное приложение, веб-интерфейс);
- модуль обрабатывает внешние данные (промокод, количество товаров, цены), поэтому необходима проверка защиты от недопустимых значений и инъекций;
- после слияния в `main` код попадает в сборку и выпуск, а исправление ошибок в основной ветви обходится дороже, чем в отдельной.

## 2. Цель ревьюирования

**Цель:** убедиться, что новая версия модуля `order_pricing` готова к включению в основную ветвь, то есть реализована корректно, безопасно, понятно и не нарушает работу остального проекта.

Для этого необходимо оценить следующие свойства реализации:

1. **Соответствие требованиям** — расчёт скидок выполняется по правилам из постановки задачи (задача №... в трекере).
2. **Корректность алгоритма** — верные формулы, округление до копеек, граничные случаи (пустой заказ, скидка 100 %, нулевая цена).
3. **Обработка входных данных** — недопустимые значения (отрицательное количество, пустой или неизвестный промокод, неверный тип) отклоняются с понятной ошибкой.
4. **Отсутствие нежелательных побочных эффектов** — изменения не ломают другие модули, обратная совместимость API сохранена.
5. **Достаточность тестов** — основные и граничные сценарии покрыты автоматическими тестами.
6. **Понятность и сопровождаемость кода** — читаемые имена, отсутствие дублирования, комментарии и документация там, где логика неочевидна.
7. **Безопасность** — в коде нет секретов, паролей и ключей, нет небезопасной обработки пользовательского ввода.

## 3. Участники процесса

| Участник | Ответственность |
|---|---|
| **Автор изменений** | Разрабатывает код и тесты, запускает локальные проверки, оформляет запрос на слияние (Pull Request) с описанием изменений, отвечает на замечания, вносит исправления и сообщает о них. |
| **Ревьюер** | Изучает diff, сопоставляет код с критериями проверки, оставляет замечания, проверяет исправления, выносит решение «одобрить» или «требуются изменения». Не является автором проверяемых изменений. |
| **Ответственный за автоматические проверки (CI-инженер / мейнтейнер конвейера)** | Настраивает и поддерживает конвейер CI (тесты, линтер, анализ безопасности), следит за актуальностью правил анализа. |
| **Ответственный за слияние (мейнтейнер репозитория)** | Проверяет выполнение всех условий допуска и выполняет слияние в `main`; при невыполнении условий возвращает изменения на доработку. |

В небольшой команде роли ревьюера и ответственного за слияние может совмещать один человек, но автор не вправе сливать собственные изменения без одобрения другого участника.

## 4. План этапов ревьюирования

| № | Этап | Ответственный | Действия | Результат |
|---|---|---|---|---|
| 1 | Подготовка изменений | Автор изменений | Проверяет код в IDE, обновляет ветвь относительно `main` (`git rebase` или `git merge main`), запускает локально тесты, линтер и форматтер, просматривает собственный diff (саморевью), убирает отладочный код | Изменения готовы к передаче, локальные проверки проходят |
| 2 | Предварительные автоматические проверки | CI-конвейер (отвечает ответственный за проверки) | После `git push` и открытия Pull Request запускает тесты `pytest`, линтер `Flake8`/`Pylint`, проверку форматирования `Black`, поиск секретов `gitleaks` | Получен отчёт CI: все обязательные проверки пройдены либо выявлены ошибки (тогда возврат автору до ревью) |
| 3 | Передача на ревью | Автор изменений | Открывает Pull Request в `main`, заполняет описание (что и зачем изменено, как проверить, ссылка на задачу), назначает ревьюера | Pull Request создан, ревьюер назначен и уведомлён |
| 4 | Изучение кода | Ревьюер | Читает описание и diff, при необходимости загружает ветвь локально и запускает код, сопоставляет изменения с критериями из раздела 5 | Составлено понимание изменений, определены проблемные места |
| 5 | Фиксация замечаний | Ревьюер | Оставляет комментарии к конкретным строкам diff, помечает серьёзность (блокирующее / рекомендация), по итогам выбирает «Request changes» или «Approve» | Все замечания зафиксированы в Pull Request, статус ревью установлен |
| 6 | Исправление проблем | Автор изменений | Анализирует замечания, вносит исправления отдельными коммитами, отвечает в обсуждениях, обновляет тесты, делает `git push` в ту же ветвь | Подготовлена обновлённая версия, в обсуждениях указано, что и как исправлено |
| 7 | Повторная проверка | Ревьюер, CI | CI запускается автоматически на новых коммитах; ревьюер просматривает только изменения после первого ревью, проверяет устранение каждого замечания и отсутствие новых проблем | Подтверждено устранение замечаний (обсуждения закрыты), проверки CI пройдены |
| 8 | Принятие решения о слиянии | Ответственный за слияние | Проверяет условия из раздела 11 (одобрение, CI, отсутствие конфликтов, закрытые замечания) и выполняет слияние либо возвращает на доработку | Изменения слиты в `main` либо возвращены автору с указанием причины |

Этапы 5–7 повторяются, пока не будут устранены все блокирующие замечания.

## 5. Критерии проверки

| № | Критерий | Конкретное требование | Способ проверки |
|---|---|---|---|
| 1 | Соответствие требованиям | Все пункты постановки задачи реализованы: применение промокода, сумма скидки не превышает стоимость заказа, формат ответа API соответствует документации | Сопоставление diff с текстом задачи и `docs/api.md`; ручной запуск эндпоинта с примерами из задачи |
| 2 | Корректность алгоритма | Результат расчёта верен для типовых и граничных случаев (пустой заказ, нулевая цена, скидка 100 %, округление до 2 знаков) | Проверка кода ревьюером, запуск тестов с граничными значениями, ручной расчёт 2–3 примеров |
| 3 | Обработка недопустимых входных данных | Отрицательное количество, неизвестный промокод, значение `None`, неверный тип данных приводят к понятной ошибке (код 400), а не к падению с кодом 500 | Тесты на негативные сценарии; ручной запрос с некорректными данными |
| 4 | Наличие тестов | Основные сценарии и граничные случаи покрыты тестами, покрытие изменённых строк не менее 80 % | Отчёт `pytest --cov` в CI, просмотр тестов ревьюером |
| 5 | Результат статического анализа | Отсутствуют ошибки уровня error/critical у `Pylint`/`Flake8`, число предупреждений не выросло | Отчёт линтера в CI (обязательная проверка) |
| 6 | Соблюдение правил оформления кода | Код отформатирован `Black`, соблюдён PEP 8, имена функций и переменных осмысленны, нет закомментированного кода и `print` для отладки | Проверка `Black --check` и `Flake8` в CI; просмотр diff |
| 7 | Обратная совместимость и отсутствие побочных эффектов | Существующие запросы к API без поля `promo_code` работают как прежде; не изменено поведение других модулей | Запуск всего набора регрессионных тестов в CI; анализ списка изменённых файлов |
| 8 | Отсутствие секретов в коде | В коде и конфигурации нет паролей, токенов, ключей | Проверка `gitleaks` в CI; просмотр diff ревьюером |
| 9 | Понятность и документация | Для нетривиальной логики есть пояснение, обновлены `docs/api.md` и описание Pull Request | Просмотр diff и документации ревьюером |

| **GitHub** (Pull Request, Issues) | Платформа для передачи изменений на ревью: показывает diff, хранит построчные комментарии и обсуждения, отображает статус проверок, управляет одобрениями и защитой ветви `main` |

## 7. Фиксация замечаний

**Где фиксируются.** Все замечания оставляются в Pull Request на GitHub, в разделе *Files changed*, а не в личных сообщениях или устно, чтобы история решений сохранялась и была доступна всем участникам.

**Как замечание связывается с кодом.** Ревьюер выделяет нужную строку (или группу строк) в diff и добавляет комментарий. Комментарий автоматически привязывается к файлу, строке и версии коммита. Для небольших исправлений используется блок предложений (*suggestion*), который автор может применить одним нажатием.

**Как автор узнаёт о замечании.** GitHub отправляет уведомление по электронной почте и в интерфейсе; в Pull Request отображается статус *Changes requested*; число незакрытых обсуждений видно в Pull Request.

**Как определяется, что вопрос рассмотрен.** Автор отвечает в обсуждении и указывает коммит с исправлением. Обсуждение помечается *Resolved* только после того, как ревьюер подтвердил исправление (для спорных вопросов — после согласования решения в ветке обсуждения). Слияние невозможно, пока остаются незакрытые блокирующие обсуждения.

**Классификация замечаний:**

- `[blocker]` — ошибка, которая должна быть исправлена до слияния;
- `[suggestion]` — рекомендация, исправление желательно, но не обязательно;
- `[question]` — вопрос, требующий пояснения автора.

**Пример корректно сформулированного комментария ревьюера** (к строке `total = price * quantity * (1 - discount)` в файле `order_pricing.py`):

> `[blocker]` В функции `calculate_total` не проверяется, что `discount` лежит в диапазоне от 0 до 1. При значении `discount = 1.5` итоговая сумма станет отрицательной, и клиент получит отрицательный счёт (проверено локально на заказе: 2 шт. по 100 руб.). Предлагаю добавить проверку и выбрасывать `ValueError` с понятным сообщением, а в API возвращать код 400. Также необходимо добавить тест на значения `discount = -0.1` и `discount = 1.5`.

Комментарий хорош тем, что указывает на конкретное место, объясняет последствия, содержит воспроизводимый пример, предлагает решение и обозначает серьёзность.

## 8. Исправление выявленных проблем

1. **Анализ замечаний.** Автор читает все комментарии, при неясности задаёт уточняющий вопрос в обсуждении. Если автор не согласен с замечанием, он обосновывает позицию в комментарии, а решение принимается по согласованию с ревьюером (при необходимости привлекается мейнтейнер).
2. **Внесение исправлений.** Автор работает в той же ветви `feature/order-pricing-v2`, каждое замечание (или логически связанная группа замечаний) исправляется отдельным коммитом с понятным сообщением, например: `fix: validate discount range in calculate_total`. История ветви не переписывается принудительно (без `git push --force`) после начала ревью, чтобы ревьюер видел, что изменилось.
3. **Локальная проверка.** Перед отправкой автор запускает тесты, линтер и форматтер.
4. **Публикация.** Автор выполняет `git push`; Pull Request обновляется автоматически, CI запускается заново.
5. **Сообщение о выполненной работе.** В каждом обсуждении автор оставляет ответ вида «Исправлено в коммите `a1b2c3d`: добавлена проверка диапазона и тест `test_discount_out_of_range`». После завершения всех исправлений автор повторно запрашивает ревью (*Re-request review*).
6. **Подтверждение устранения.** Замечание считается устранённым после того, как ревьюер проверил исправление и закрыл обсуждение (*Resolve conversation*), а связанные автоматические проверки пройдены.

## 9. Повторное ревьюирование

После внесения исправлений ревьюер проверяет следующее:

1. **Устранение исходной проблемы.** Для каждого замечания ревьюер открывает указанный автором коммит, убеждается, что исправление решает проблему по сути, а не формально, при необходимости воспроизводит исходный сценарий (например, повторяет запрос с некорректной скидкой). Для этого используется просмотр только новых коммитов (*Changes since last review*).
2. **Отсутствие новых ошибок.** Ревьюер просматривает diff исправлений на предмет побочных эффектов: не изменено ли поведение соседних функций, не нарушены ли критерии 1–9 в новом коде, не появились ли лишние файлы или отладочный код.
3. **Результаты автоматических проверок.** В Pull Request проверяется, что на последнем коммите все обязательные проверки CI завершились успешно: тесты проходят (включая новые тесты на исправленные случаи), линтер не выдаёт ошибок уровня error/critical, форматирование соответствует `Black`, `gitleaks` не нашёл секретов, покрытие изменённого кода не ниже 80 %.
4. **Актуальность относительно `main`.** Ветвь не отстаёт от `main` настолько, чтобы появились конфликты слияния; при наличии новых изменений в `main` автор обновляет ветвь и ревьюер проверяет результат обновления.
5. **Решение.** Если проблемы остались или появились новые, ревьюер оставляет новые замечания, и цикл повторяется. Если всё в порядке — выставляет статус *Approve*.

## 10. Правила доступа к репозиторию

| Действие | Автор изменений (разработчик) | Ревьюер (разработчик, не автор) | Ответственный за слияние (мейнтейнер) | Администратор репозитория |
|---|---|---|---|---|
| Читать код | Да | Да | Да | Да |
| Изменять код в собственной feature-ветви | Да | Нет (только через предложения в Pull Request) | Да | Да |
| Создавать ветви | Да (по соглашению об именах `feature/*`, `fix/*`) | Да | Да | Да |
| Открывать Pull Request | Да | Да | Да | Да |
| Оставлять комментарии в Pull Request | Да | Да | Да | Да |
| Одобрять изменения (*Approve*) | Нет (свои изменения не одобряет) | Да | Да (если не автор) | Да (если не автор) |
| Выполнять слияние в `main` | Нет | Нет | Да | Да |
| Изменять настройки репозитория и защиты веток | Нет | Нет | Нет | Да |

**Обязательные правила:**

1. **Запрет прямых изменений основной ветви.** Для `main` включена защита ветви (*Branch protection rules*): прямой `git push` в `main` и принудительная перезапись истории (`--force`) запрещены для всех, включая администраторов; изменения попадают в `main` только через Pull Request.
2. **Обязательные условия слияния** настроены на уровне платформы: минимум одно одобрение ревьюера, успешное прохождение проверок CI, закрытие всех обсуждений, актуальность ветви относительно `main`.
3. **Автор не может одобрить и слить собственный Pull Request** без участия другого человека.
4. **Запрет на передачу личных учётных данных.** Участники не передают друг другу пароли и персональные токены доступа; доступ предоставляется индивидуально через учётные записи и роли платформы, для работы по SSH используются персональные ключи, для двухфакторной аутентификации — включена обязательная настройка.
5. **Запрет на включение секретов в исходный код.** Пароли, токены, ключи API и строки подключения к БД хранятся в переменных окружения или в хранилище секретов (*GitHub Secrets*), в репозиторий попадает только шаблон конфигурации (`.env.example`). Файлы с секретами добавляются в `.gitignore`; проверка `gitleaks` в CI блокирует слияние при обнаружении секрета. Если секрет всё же попал в коммит, он считается скомпрометированным и немедленно заменяется.
6. **Принцип минимальных привилегий.** Каждому участнику выдаются только те права, которые необходимы для его роли.

## 11. Итоговое решение

**Условия принятия изменений.** Изменения допускаются к слиянию в `main`, только если одновременно выполнены все требования:

1. Устранены все существенные (блокирующие) замечания, соответствующие обсуждения закрыты ревьюером.
2. Все обязательные автоматические проверки на последнем коммите пройдены: тесты, линтер, проверка форматирования, поиск секретов, покрытие тестами не ниже 80 %.
3. Получено необходимое одобрение: минимум одно *Approve* от ревьюера, не являющегося автором.
4. Отсутствуют неразрешённые конфликты слияния, ветвь актуальна относительно `main`.
5. Описание Pull Request и документация API актуальны.

Если хотя бы одно условие не выполнено, изменения возвращаются автору на доработку с указанием причины.

**Вывод.** Ревьюирование не должно ограничиваться чтением исходного кода. Человек эффективно оценивает логику, соответствие требованиям и понятность, но может пропустить ошибки форматирования, нарушения стиля, утечку секретов или регрессию в других частях проекта, поэтому такие проверки поручаются автоматическим средствам (тесты, статический анализ, поиск секретов): они выполняются одинаково и быстро при каждом изменении. Управление изменениями (защита основной ветви, обязательные одобрения, классификация замечаний, закрытие обсуждений) превращает ревью из формальности в обязательный этап процесса и сохраняет историю принятых решений. Повторная оценка исправлений необходима потому, что исправление одной ошибки может создать новую, а замечание нельзя считать устранённым, пока это не подтверждено проверкой.

Система контроля версий Git и платформа GitHub создают основу всего процесса: изолируют изменения в отдельной ветви, показывают точный diff, хранят историю исправлений, связывают замечания с конкретными строками кода и позволяют технически запретить слияние без выполнения условий. Остальные инструменты (VS Code, pytest, Pylint/Flake8, Black, gitleaks, GitHub Actions) обеспечивают проверку по конкретным критериям, а их результаты отображаются в одном месте — Pull Request, что делает решение о слиянии обоснованным и прозрачным.
